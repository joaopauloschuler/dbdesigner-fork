### 2. Canvas keeps a stale horizontal line after a table is renamed/resized through the Table Editor

Severity: cosmetic.
Steps: open order.xml; double-click `productgroup`; change the Table Name to `productgroup_renamed` (table becomes wider); OK.
Observed: the table, the DB Model tree and the `ProductgroupRel` line update correctly, but a light grey 1-px horizontal line remains across the whole `OnlineStore` region at canvas y~503 (from the region's left edge to its right edge, `12-main-after.png`). Expected: no leftover pixels after the editor closes.
Suspected cause: the invalidate rectangle after `EditorTable` closes (`TEERTable.RefreshObj`/`DoPaint` in `src/EERModel.pas`) covers the old table bounds only, while the region background is redrawn with an off-by-one row (or the selection frame of the table is cleared with the region's colour minus one line). Status: fixed in 3d2c6f3 - not an invalidation problem: the white 190-px line at y=502 is the `RelEnd` paintbox of the *splitted* `forumpost` relation (onlinecustomer -> forumpost). `TEERRel.PaintObj2Canvas_RelStart/_RelMiddle/_RelEnd` read `width`/`height` inside `with RelEnd do with theCanvas do`, which the LCL resolves to `TCanvas.Width/Height` (GDK drawable size 3072, or 0 before the handle exists). `TEERRel.DoPaint` paints RelEnd through `RelEnd.Canvas`: the first `width` read gives 0 (`w:=-1`), `MoveTo` allocates the handle, `LineTo(xo+width-1-w)` then draws the white "clear" pass from -1 to 3072 clipped to the control, and the black dash-dot-dot pass lands off-clip. It shows after the Table Editor OK because that path repaints directly outside an expose. The painters now capture the control size first; the splitted stubs and end icons appear too. Verified with two renames and a table drag (`fix02-04-07/30-fixed1/2`, `31-moved.png`). See notes-to-myself.md "Fix: model-edit #2, #4, #7".

### 20. Table Editor: a comment typed into a cell while the new-row Column Name editor is open keeps only its first character

Severity: functional (silent data loss of the comment text).
Steps: commit a column name or a datatype on the last row with Return so the empty new row opens its Column Name editor (cursor visible in the diamond row); click the Comments cell of an existing row; type `c-extra`, Return.
Observed: the cell reads `c` (`m1.png` row `name`, `m7.png` top row `extra`); repeated 2/2 under this condition, plus round 6 observation (b). When no new-row editor is open the same sequence keeps the full text (`m7.png` bottom, `c-name` retyped; `c-flag`, `c-notes`, `c-price`).
Suspected cause: the first keystroke reaches the grid (`ColumnGridKeyDown` -> `EditCellStr(NewName)` with the one character) while the still-open `EditorTableFieldEdit` of the new row is closed/re-parented by the click; the remaining keystrokes arrive before the new editor has focus and are dropped. Not confirmed by a probe. Fix scope: small (close the pending editor in `ColumnGridMouseUp`/`SelectCell` before starting the next, or give the new editor focus synchronously).
Status: fixed - stuck mouse capture, not a focus race. Probes (`gtk_grab_get_current`, `GetCaptureControl`) showed that after the click the grid kept the LCL mouse capture (GTK grab on the grid widget) for good: the click's button press first moved the focus off the open editor, whose `OnExit` -> `ApplyChanges` -> `HideEdit` ran `Application.ProcessMessages` (a CLX-era workaround) *inside* the grid's button-press handling, so the button *release* was processed before the LCL took the capture for the press and nothing released it afterwards. Every following key press was then emitted on the grabbed grid widget; the LCL redirected the LM_KEYDOWN to the focused editor (its `OnKeyDown` fired, hence the "no emission of signal key-press-event to stop" GLib-CRITICAL on each key) but the GtkEntry itself never received the key, so only the first character (inserted through `ColumnGridKeyDown` -> `EditCellStr('c')`) survived; Return still worked because it is handled in `OnKeyDown`. Fix: `HideEdit` no longer pumps the message queue (`src/EditorTableField.pas`). Verified on the real display (`shots/fix20/`): the exact repro (`zz1` + `VARCHAR(7)` typed + Return -> new-row editor open, click `name` Comments, `c-extra` + Return) keeps `c-extra` (`a12.png`), Tab from an existing row's name through DataType and Default Value into Comments takes `via-tab` (`b012.png`), Column Name / DataType typing unchanged (no doubling, no loss), OK + Ctrl+S + reopen shows all of it (`c1-reopened-c.png`, `fix20.xml`), and the GLib-CRITICAL lines of #14 did not appear once in the run.
